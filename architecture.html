Rose — the VM agent 🌌

An AI agent that lives on its own Ubuntu VM (locally or on EC2), uses the computer like you do — sees the XFCE screen, moves the mouse, types — performs your instructions, and learns repeatable tasks from narrated video recordings. The agent is Rose; the service that runs it is rosed.

Settled decisions (this revision)
  • Desktop-only control for the prototype. One X11 screenshot + input loop drives everything — Chromium (most workflows are web UIs anyway), native apps, dialogs, file pickers. No separate browser controller, no CDP layer in v1.
  • No third-party agent frameworks (browser-use, Cua, OpenAdapt, UI-TARS, Playwright-agents, etc.). Everything that decides or acts is first-party code. A CDP/browser backend may be added later, behind the same interface, only if measured pixel-reliability demands it (§9).
  • One stack everywhere: Ubuntu Server → XFCE running on TigerVNC Xvnc (DISPLAY=:1) — identical on a local VM and EC2 (§2). No VM snapshots, no golden images, no Docker.
  • rosed = one Rust binary. X11 controller, agent loop, Governor, Web UI, API, SQLite state — single static binary under systemd --user. Python returns only as the offline video worker in Phase 2 (§7).
  • Interface = a single-page Web UI (§5): instruction in, live desktop + step timeline out, approvals and takeover inline.
  • Models: Meta AI only. Phase 1 uses one: Muse Spark 1.3 (Contributor tier) — screenshot in, one JSON action out. Muse Voice and SAM 3.1 arrive in Phase 2+.

There is no separate control-plane host in v1. rosed on the VM serves the UI, runs the agent, and stores everything. If that ever needs to split, the UI↔rosed API is the seam — but don't build for it now.

How Rose sees and acts (the only mechanism in v1)

observe() -> { screenshot, elements: [{id, label, bounds, confidence}],  // vision-derived
               active_window, screen_size }                             // from X11/EWMH

act({ target: element_id | {x, y},
      action: "click" | "double_click" | "type" | "press_key" |
              "scroll" | "drag" | "wait",
      text? }) -> { ok, error? }
  • Capture: X11 GetImage of the Xvnc root window, encoded JPEG. Fixed resolution (1600×900) so coordinates are stable.
  • Coordinates: in Phase 1 the model looks at the screenshot and replies with the click point directly (fixed 1600×900 screen, so pixel coordinates are stable). No element-extraction system yet — the next screenshot is how Rose sees whether it worked. SAM 3.1 precision grounding is added in Phase 2/3 for learned skills.
  • Input: XTEST synthetic pointer/keyboard (works on every X11 app). Human takeover sends input through the same path with actor:"human" — one input channel, one audit log.
  • One atomic action per act() — gated, logged, verified individually. No blind batched clicking. This is what makes runs debuggable and (later) replayable.

3. rosed — one Rust binary

Chosen because the on-VM component is a long-lived daemon doing X11, streaming, HTTP/WebSocket, and policy enforcement — the "if it compiles, it works, ship one binary" profile. (x11rb provides capture/XTEST/EWMH; Tokio for concurrency; model calls are HTTPS+JSON, so Rust costs nothing on the AI side. Prompts live in reloadable files — tuning them never needs a recompile. Go was rejected: weaker X11 ecosystem, no compensating win.)

Module (in the one binary)Responsibility
x11-controllerCapture, XTEST input (click/type/key/scroll/drag), active-window info, coordinate mapping. The only module that touches the desktop.
agent-loop§4 loop (screenshot → model → action → screenshot); budgets; Stop handling.
governorDeterministic policy gate before every action (§4): approvals, allowlists, redaction, budgets, kill switch. Pure rules, no LLM — a model never approves its own action.
webEmbedded static UI (no Node build step), HTTP API, WebSocket event/frame stream.
storeSQLite: tasks, runs, steps, skills; artifact files (frames, downloads, recordings).
Python video worker Phase 2, invoked by rosedOffline pipeline (§7): ffmpeg + frame analysis + Muse Voice/Spark/SAM calls. Exploratory CV glue lives here, off the always-on path — the one place Python's speed of iteration wins.

API surface (UI and any future CLI share it): POST /tasks · POST /tasks/:id/stop · POST /runs/:id/approve|deny · POST /desktop/takeover|handback · WS /events (run steps, approvals, status) · WS /desktop/frames (live view + human input when holding the lease). Session-token auth; localhost + tunnel is the perimeter.

Control lease: exactly one driver — Rose or you (via Rose live view input, or a directly connected VNC client). 7. Phase 2 — narrated video → Skill

You record yourself doing a task while narrating it (“filter by March — this changes monthly — then Export, CSV”). Narration is the primary semantic signal: intent, step names, and which values are variables come from the Muse Voice transcript, timestamp-aligned to the screen. Vision only answers where exactly and what changed.

  • Event detection is deliberately classical (cursor dwell + localised change ≲300 ms = click candidate; text growth = typing). It proposes; Muse Spark decides semantics. Narration/screen disagreements are surfaced in Studio, never silently resolved.
  • Synthesis: literals the narration marks as changeable → {{parameters}} (recorded value = default); secret-looking input → human_input placeholders, never stored; probable demonstrator mistakes flagged for deletion.
  • Every step keeps evidence: {video_ts, narration_quote, target_crop} and a confidence score driving Studio highlighting + confirm-at-replay defaults. Timestamp granularity from Muse Voice (word vs segment) sets alignment precision — open decision (§11).
  • The pipeline replays naturally onto Phase 1: recordings are pixels, Rose acts on pixels — same surface, no second execution model.

8. Phase 3 — skill execution

A published Skill is exposed to the planner as one tool (skill.export_invoices(month=…)) beside raw observe/act; retrieval starts as keyword + Muse Spark rerank over skill descriptions.

ModeHow it runs
Semantic replay (universal)The §4 loop executes the DSL, re-grounding every step live from vision. Works day one of Phase 3; tolerates moved UI via planner escalation within budget.
Deterministic replay (fast path)rosed already logs every act() with its target descriptor (§4 traces). A verified run's trace is replayed with new parameter values at ~zero model calls, halting at the first mismatch; uncertain writes are never auto-retried (“check the record” outcome for the human).
RepairHalted step → semantic retry of its intent under the same approvals → proposed Skill v+1 diff, human-approved. Skills are never silently rewritten.

Read-back verification: postconditions check the real record (downloaded file on disk, new list row, confirmation number) — not an on-screen “Saved ✓” toast. Scheduling (cron/webhook → task from a Skill) is a thin add-on once replay is trustworthy.

skill: export-invoices
version: 3
source: { recording: rec_abc123, reviewed_by: human }
parameters:
  month:      { type: month, default: "previous" }
  output_dir: { type: path,  default: "~/Downloads/invoices" }
preconditions:
  - browser_logged_in: billing.example.com     # unmet -> waiting_human
steps:
  - intent: "Open the billing portal"
    evidence: { video_ts: "00:12", narration: "I'm opening the billing portal" }
    action: navigate_via_desktop               # open Chrome, type URL
    postcondition: "billing portal visible"
  - intent: "Go to Invoices"
    evidence: { video_ts: "00:31", narration: "go to Invoices" }
    action: click
    locator: { visual: { anchor_text: "Invoices", near: "top navigation" } }
    postcondition: "heading 'Invoices' visible"
  - intent: "Set the month filter"
    evidence: { video_ts: "01:05", narration: "filter by month - changes every time" }
    action: select_or_click
    locator: { visual: { anchor_text: "Month" } }
    args: { value: "{{ month }}" }
    postcondition: "rows for {{ month }} visible"
  - intent: "Download the CSV"
    evidence: { video_ts: "01:40", narration: "Export, then CSV" }
    action: click
    locator: { visual: { anchor_text: "Export CSV" } }
    approval: required
    postcondition: "new .csv exists in {{ output_dir }}"   # read-back
outputs: { file: "{{ output_dir }}/*.csv (newest)" }
on_failure: halt_and_ask

9. Safety & what comes later

RiskMitigation
Privileged desktop sessionDedicated VM = blast radius; allowlists; reinstall = clean state.
Prompt injection from screen contentObservations are data, never instructions; planner forbids obeying on-screen instructions; cross-policy actions still hit the Governor + approval. (Unsolved in general — the gate is the defence.)
SecretsLogins live in the browser profile; Rose uses the session. Frames redacted in-VM; traces store parameter slots, not secrets; recordings/traces sensitive at rest.
Irreversible / confidently-wrong actionsApproval gates; halt-on-mismatch; uncertain writes = “check the record”, never auto-retried; read-back postconditions.
Runaway / costKill switch, per-run step/time/spend budgets, one run at a time.
ExposureLocalhost + Tailscale/SSH only; session auth; full audit trace per run.

Later, only on evidence: CDP/browser backend behind the same observe()/act() — if the measured pixel-step failure rate on your real workflows is too high, observe() for a Chromium window starts returning structural elements and everything else (loop, Governor, DSL, UI) stays untouched. Also later: voice-first interaction, phone push approvals, richer live view. None of it is in the prototype's way.

10. Roadmap with exit tests

Phase 1 — Rose works

  1. Setup script on a fresh Ubuntu Server (VM and an EC2 instance) → XFCE/Xvnc + Chrome + rosed; human first-login via VNC.
  2. Hands test (no LLM): UI streams frames; clicking/typing in the live view drives the desktop. Proves capture+input+lease before any model is attached.
  3. Agent loop + Governor; Web UI per §5. (SAM arrives in Phase 2.)

Exit: “Download the latest invoice from the portal I'm logged into” + “Create a folder and move Downloads' PDFs into it” + 6–8 more of your real tasks complete from the Web UI at ≥80% success, ≤1 approval each on gated steps; Stop halts input <1 s; takeover/hand-back mid-run works; every step shows before/after evidence.

Phase 2 — narrated video → Skill

Exit: a 3–5 min narrated recording yields a draft needing ≤5 min of correction; every step links to its video moment + narration line; changeable values correctly parameterised in the common cases.

Phase 3 — Rose uses Skills

Exit: “Export the invoices for March” (never recorded) runs end-to-end; a deliberately renamed button halts before any write with a repair proposal; an unchanged skill's repeat run uses ~zero planner calls in deterministic mode.

11. Risks & open decisions

ItemPosition
Pixel grounding reliability (wrong look-alike click)The known cost of desktop-only. Contained by: fixed 1600×900, maximised windows/100% zoom, verify-on-next-screenshot with re-try (SAM refinement joins in Phase 2/3). Measured in the Phase 1 exit set; the CDP escape hatch (§9) exists if the number is bad.
Muse Voice timestamp granularityConfirm word- vs segment-level; sets Phase 2 alignment precision. Blocks final Phase 2 design, not Phase 1.
Vision cost per stepEvery step is a frame → Muse Spark call. Budgets in the Governor; candidate-element caching within a screen is an optimisation only if spend demands it.
Deterministic trace formatDesign in Phase 3 from real Phase 1 traces, not upfront.
Chrome vs Chromium on UbuntuChrome .deb default (Snap pain). Revisit only if a hard Chromium requirement appears.

Glossary — Rose: the agent. rosed: its Rust service (one binary, systemd --user). Governor: deterministic policy gate before every action. Lease: single-driver token (Rose or human). Skill: reviewed, parameterised, evidence-linked procedure (§8). Read-back: verify in the record, not from a toast.
